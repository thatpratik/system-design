## What is a Rate Limiter?

A rate limiter controls how many requests a client can make in a given time window. When a client exceeds its quota, the rate limiter rejects further requests — typically with a `429 Too Many Requests` response — and includes a `Retry-After` header indicating when the client may try again.

Rate limiting protects APIs from abuse, prevents a single client from monopolising server resources, and provides fairness between users.

## Problem it Solves

Without rate limiting:

- A buggy client sends 10,000 requests per second, taking down a service for all users
- A competitor scrapes your entire product catalog overnight
- A user guesses passwords in a brute-force loop with no friction
- A sudden traffic spike overwhelms downstream databases

Rate limiting is the first line of defence at the API layer.

## Algorithms

| Algorithm | How it works | Burst handling | Memory | Accuracy |
|---|---|---|---|---|
| **Fixed Window** | Count resets every N seconds on the clock boundary | Allows 2× burst at window boundaries | Low (one counter) | Poor at edges |
| **Sliding Window Log** | Store timestamp of every request; count events in rolling window | Accurate, no burst at boundaries | High (one entry per request) | Exact |
| **Sliding Window Counter** | Two fixed-window counters weighted by time overlap | Good burst control, approximated | Low (two counters) | ~1% error |
| **Token Bucket** | Tokens refill at a fixed rate; each request consumes one | Allows bursts up to bucket capacity | Low (count + timestamp) | Good |
| **Leaky Bucket** | Requests added to a queue; processed at a fixed output rate | No burst — smoothed output | Low | Exact output rate |

The **sliding window counter** is the most popular choice for API rate limiting: low memory, near-exact accuracy, and no boundary spike.

## How it Works (Sliding Window Counter)

Using Redis as the backing store, each client gets two counters: one for the current minute and one for the previous minute.

```
current_rate = prev_count × (1 − elapsed_fraction) + curr_count

Example:
  limit            = 100 req/min
  prev_count       = 80  (requests in the previous minute)
  curr_count       = 40  (requests in the current minute so far)
  elapsed_fraction = 0.3 (30 seconds into the current minute)

  current_rate = 80 × 0.7 + 40 = 56 + 40 = 96

  96 < 100  →  allow the request
```

Redis operations per request:
1. `INCR key:curr` — increment current window counter
2. `EXPIRE key:curr 120` — ensure cleanup after two windows
3. `GET key:prev` — read previous window count
4. Apply formula; allow or reject

## Distributed Rate Limiting

Per-server counters fail in a distributed system — each server only sees its own traffic:

```
Client with limit = 100 req/min

Without shared state:
  Server A: sees 60 requests  →  allows all (60 < 100)
  Server B: sees 60 requests  →  allows all (60 < 100)
  Total delivered: 120 requests — limit violated
```

The fix is a **centralised Redis cluster** shared by all servers. Redis's atomic operations prevent race conditions:

```lua
-- Lua script executed atomically on Redis
local current = redis.call('INCR', KEYS[1])
if current == 1 then
  redis.call('EXPIRE', KEYS[1], ARGV[1])
end
if current > tonumber(ARGV[2]) then
  return 0  -- over limit
end
return 1  -- allowed
```

## Key Design Decisions

### Where to enforce

| Location | Pros | Cons |
|---|---|---|
| **API Gateway** | Enforced before requests reach services; single config point | Gateway must have access to the rate-limit store |
| **Application layer** | Fine-grained logic, per-route rules | Must implement in every service |
| **Load balancer** | Very early rejection; low overhead | Limited to IP-based rules |

Most production systems enforce at the API Gateway for coarse limits (IP / API key) and optionally at the application layer for fine-grained per-endpoint rules.

### Granularity

- **Per IP**: Coarsest. Effective against scraping but penalises shared NATs.
- **Per API key / user ID**: Most common for authenticated APIs. Fair per-client limits.
- **Per endpoint**: Different limits for expensive operations (`POST /search` = 10/min) vs cheap ones (`GET /status` = 1000/min).

### Response headers

Always include these headers so clients can self-throttle:

```
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 37
X-RateLimit-Reset: 1719662400
Retry-After: 23
```

## Trade-offs

| | Benefit | Cost |
|---|---|---|
| **Protection** | Prevents abuse and runaway clients | Legitimate burst traffic may be blocked |
| **Fairness** | No single client can starve others | Per-user state adds Redis dependency |
| **Simplicity** | Redis counters are easy to implement | Distributed race conditions require atomic operations |
| **Accuracy** | Sliding window is close to exact | Approximate algorithms have edge cases at window boundaries |

## Real-World Usage

- **Stripe**: Token bucket per API key; publishes rate limit headers on every response; documents the algorithm publicly in their engineering blog
- **GitHub API**: 5,000 requests per hour per authenticated user; unauthenticated requests get 60 per hour
- **AWS API Gateway**: Per-stage and per-route throttling with burst limits configurable in the console
- **Cloudflare**: Operates rate limiting at the edge before traffic reaches origin, handling millions of rules globally
