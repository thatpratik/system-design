## The Scaling Ladder

Database scaling is not one decision — it is a sequence of increasingly complex interventions. Each level buys more headroom. The goal is to stay at the simplest level that meets your requirements.

```
Level 0  ──  Single primary (where everyone starts)
Level 1  ──  Vertical scaling        (bigger machine)
Level 2  ──  Connection pooling      (more efficient use of the same machine)
Level 3  ──  Read replicas           (scale reads horizontally)
Level 4  ──  Caching layer           (absorb hot reads before they hit the DB)
Level 5  ──  CQRS / read models      (purpose-built read stores)
Level 6  ──  Sharding                (scale writes horizontally)
```

Most applications never need to go past Level 3. Measure before moving up.

---

## Vertical Scaling

Scale up the machine the database already runs on. No new instances, no topology changes, no application code changes — just more resources on the same node.

**Ceiling:** Bounded by the largest available machine. Cloud instances top out, and the cost curve is non-linear — the largest instance may cost 8× the next tier while delivering 2× improvement. Once you hit that ceiling, the only path forward is horizontal.

**When to apply:** Always exhaust vertical options before introducing horizontal complexity. The operational overhead difference is enormous.

---

### Level 1 — Hardware Upgrade

Give the database more CPU, RAM, and faster disks.

**What it fixes:** The database is CPU-bound (complex queries), I/O-bound (buffer pool too small for the working set), or hitting disk throughput limits.

**How RAM helps:** The database buffer pool caches hot data pages in memory. Doubling RAM can eliminate a large fraction of disk reads if the working set fits. A common rule of thumb: if your buffer pool hit rate is below 95%, more RAM will help more than a faster disk.

---

### Level 2 — Connection Pooling

Every database connection consumes memory on the server (PostgreSQL uses ~5–10 MB per connection). Applications with many concurrent threads or serverless functions can exhaust available connections before hitting any CPU or I/O limit.

A **connection pooler** sits between the application and the database, multiplexing many application connections onto a smaller pool of actual database connections.

```
  App server 1 ──┐
  App server 2 ──┼──► PgBouncer / ProxySQL ──► DB Primary (20 real connections)
  App server 3 ──┘
  (300 app-side connections)
```

| Pooler | Mode | Notes |
|---|---|---|
| **PgBouncer** | Transaction pooling | Lowest overhead; connection returned to pool after each transaction |
| **ProxySQL** | Session / transaction | MySQL-focused; also does query routing |
| **RDS Proxy** | Session pooling | Managed AWS option; integrates with IAM and Secrets Manager |
| **pgpool-II** | Session / transaction | Also handles load balancing and failover |

**Transaction pooling** (PgBouncer's default) is the most efficient: a connection is held only for the duration of one transaction, then returned. This allows thousands of app connections to share tens of database connections.

**What to watch:** Transaction pooling is incompatible with session-scoped features like `SET LOCAL`, advisory locks, and prepared statements that persist across transactions.

## Horizontal Scaling

Add more machines to share the load. No hard ceiling — you can keep adding replicas, cache nodes, or shards as demand grows.

**The fundamental trade-off:** A single machine is trivially consistent. The moment you distribute state across multiple nodes, consistency becomes something you actively manage. Replicas may lag behind the primary, caches may hold stale data, shards cannot easily answer queries that cross partition boundaries. Every horizontal technique below is a point on the consistency-vs-scalability spectrum — choose based on what your application can tolerate.

Levels 3–5 scale **reads**. The primary still handles all writes, so write throughput is unchanged. Level 6 is the only technique that scales **writes**.

---

### Level 3 — Read Replicas

The primary handles all writes. Replicas receive a stream of changes (WAL in PostgreSQL, binlog in MySQL) and apply them asynchronously, staying nearly in sync.

```
          Writes
            │
        ┌───▼────┐
        │ Primary │──── replication stream ────►  Replica 1
        └─────────┘                           └►  Replica 2
                                              └►  Replica 3
          Reads
            │
    ┌───────┼───────┐
    ▼       ▼       ▼
 Replica 1  2       3   (load-balanced)
```

**What it fixes:** Read throughput. Each replica adds independent read capacity. This is the correct solution for read-heavy workloads (reporting, search, dashboards, user-facing feeds).

**Replication lag:** Replicas are eventually consistent. A write to the primary may not be visible on a replica for milliseconds to seconds, depending on load.

Mitigation strategies for lag:
- **Read-your-writes consistency:** Route a user's reads to the primary (or the same replica) immediately after they write.
- **Lag-aware routing:** Query `pg_stat_replication` / `SHOW SLAVE STATUS` and skip replicas that are behind by more than a threshold.
- **Synchronous replication:** One or more replicas can be made synchronous (commit waits for acknowledgment). This eliminates lag at the cost of write latency.

**How many replicas:** One replica covers most read-heavy apps. Add a second for HA failover. Beyond two, consider whether a caching layer (Level 4) would be cheaper.

---

### Level 4 — Caching Layer

A cache (Redis, Memcached) sits in front of the database and serves frequently read data from memory without touching the database at all.

```
Client ──► Cache (Redis)
              │ hit: return immediately
              │ miss: read from DB, populate cache, return
              ▼
           Primary / Replica
```

**What it fixes:** Hot-spot reads — the same rows or queries being repeated many times per second. A well-tuned cache can reduce database read load by 80–95%.

**Cache-aside pattern (most common):**

```
value = cache.get(key)
if value is None:
    value = db.query(...)
    cache.set(key, value, ttl=300)
return value
```

**What caching does not fix:** Write throughput. Every write still hits the primary. Caching only deflects reads.

**Invalidation:** The hardest part. Options:
- **TTL-based:** Entries expire after N seconds. Simple but serves stale data up to TTL.
- **Write-through:** Invalidate or update cache on every write. Consistent but adds write-path complexity.
- **Event-driven:** Database triggers or CDC (Change Data Capture) emit events that invalidate cache entries.

---

### Level 5 — CQRS and Purpose-Built Read Models

**Command Query Responsibility Segregation (CQRS)** separates the write model (commands, normalised RDBMS) from the read model (queries, denormalised store optimised for specific access patterns).

```
Write path:   API ──► Command Handler ──► RDBMS (normalised, ACID)
                                            │
                                            └── event / CDC stream
                                                     │
Read path:    API ──► Query Handler  ──► Read Store ◄┘
                                         (Elasticsearch, Redis, DynamoDB,
                                          or a denormalised Postgres table)
```

**When to use:** When the read access pattern is fundamentally different from the write model:
- Full-text search → Elasticsearch / OpenSearch
- Aggregated dashboards → a materialized summary table or a columnar store
- Low-latency personalised feeds → a Redis sorted set pre-computed at write time

**Cost:** The write path must propagate changes to the read model. This adds latency, a synchronisation component that can fail, and eventual consistency between command and query sides.

---

### Level 6 — Sharding

The only technique that scales **writes**. When writes saturate the primary and vertical scaling has no room left, the write workload is split across multiple independent database instances. Each instance (shard) owns a partition of the data.

This is covered in depth in the [Database Sharding](/components/database-sharding) component. The key point in the scaling context:

- Sharding is a last resort, not a starting point.
- It eliminates cross-shard JOINs and distributed transactions.
- It constrains the data model permanently around the shard key.
- Exhaust Levels 1–5 before committing to it.

## Decision Framework

| Symptom | Likely Bottleneck | First Action |
|---|---|---|
| Queries slow despite indexes | CPU / buffer pool too small | Vertical scale (more RAM) |
| `too many connections` errors | Connection exhaustion | Add PgBouncer |
| High read latency, low write volume | Read throughput | Add read replica |
| Same rows/queries hit repeatedly | Hot-spot reads | Add caching layer |
| Write latency growing under load | Write throughput on primary | Check indexes, then consider CQRS or sharding |
| Disk I/O at ceiling | Working set larger than RAM | Vertical scale or add read replicas to distribute I/O |

**The rule:** measure first. `pg_stat_statements`, `EXPLAIN ANALYZE`, and slow query logs tell you exactly which query is the problem and why. Never choose a scaling tier based on intuition alone.
